# Data API caller-permission migration

The `20261124000100`–`20261124001200` migrations change the 32 `saais_api` views to `security_invoker` while retaining their security barriers. The public views continue to require an authenticated account and preserve their previous role and student scopes.

The caller now needs column-level `SELECT` grants on the underlying tables and row-level policies that match each published projection. This intentionally makes those granted columns available through the `public` schema when that schema is exposed; the policies apply to those direct reads too. Columns not in the published projections, such as INC resolution reasons, adviser-assignment reasons and raw audit snapshots, remain unavailable through direct table reads. Profile `entry_year` remains ungranted and is returned only through the scoped organization helper. The audit display helper returns old/new snapshots only to an authorized administrator. Other helpers in `saais_private` return only values already published in their corresponding scoped views and independently check authorization, including for direct SQL calls.

Before applying these migrations, verify the target Supabase project and its migration history, inspect any policies and column grants added outside the repository, and reconcile drift. PostgreSQL policies are permissive by default and combine with OR: an additional broad hosted policy could expand direct table reads. Existing column-level grants can also expose additional fields. Do not apply these migrations until the effective hosted policies and grants have been reviewed. In particular, keep `saais_private` out of the Data API exposed schemas.

After applying, verify scoped Data API reads and direct-table denials with student, adviser, department staff, department head, dean, administrator, disabled and anonymous sessions; exercise former-adviser and cross-department cases. Check the security advisor after its next refresh. These migrations do not change hosted API settings, Auth, Storage, Edge Function secrets or deployment configuration, and they do not resolve unrelated advisor findings.

## Resource controls boundary

Contracted reads use `Accept-Profile: saais_api`. The shared client routes them through the `data-api` Edge Function, which validates the frozen contract's query names, flat projections, ordering, and pagination before forwarding to PostgREST. Collection reads use the URL's `limit` and `offset` parameters and default to 20 rows. The gateway expands an omitted or wildcard projection to the contract's explicit fields. The forwarded caller JWT continues to enforce row scope, and PostgREST caps responses at 1,000 rows.

Migration `20261126002300` registers a PostgREST pre-request guard. Browser roles need the gateway's server-only credential for direct collection reads, including requests that omit the schema header. Trusted service clients use their existing grants. Existing `public` RPCs are outside the collection gateway and retain their own SQL grants and authorization checks. The Edge Function obtains the generated gateway credential using Supabase's service role and never returns it to callers.
