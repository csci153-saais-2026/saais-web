# Student photo validation

The private `student-photos` bucket is created by migration `20261122000400`; migration `20261124001300` raises its limit to 5 MiB. No manually created bucket is required when both migrations have been applied. The later migration also updates the database's pinned request-schema copies to accept 5 MiB. The source OpenAPI contract documents the new limit, while the original pinned 0.3.1 snapshots remain historical.

The existing client first uploads a staging object and requests the photo update. The `students` Edge Function checks the caller and its request budget, reads the staged bytes using the caller's credentials, checks the size and file signature, decodes the PNG or JPEG with a 16-million-pixel limit, and writes those same validated bytes to a new protected object using the server-side service credential. Only the service role can register a short-lived one-use authorization for that object. The regular caller-scoped RPC consumes the authorization, rechecks scope and stored metadata, and updates the profile. Restrictive Storage policies prevent browser roles from writing or deleting protected objects.

Deploy the database migration and the updated `students` Edge Function together. The database migration makes older function deployments reject photo updates; the updated function also requires the new database functions. Confirm that the Edge Function has the platform-provided `SUPABASE_SERVICE_ROLE_KEY`, and keep that credential server-side. Verify the new `saais_photo_upload_authorize` and `saais_register_verified_photo` RPCs are reachable through the Data API with their respective authenticated-only and service-role-only grants; granular function exposure settings may need to be configured in the target project. The Edge Function uses the exact pinned ImageScript version in its Deno import map and lockfile. Verify real JPG, PNG, spoofed, oversize, direct-RPC, cross-student and retry cases in the target test project before release.

The frontend stages uploads under a fresh `upload-<uuid>.jpg` or `upload-<uuid>.png` path with overwrite disabled. Migration `20261126001700` reserves each of these names permanently, so deferred cleanup cannot remove a later upload at the same path. Older clients can still send shared staging paths. Automatic replacement cleanup leaves those reusable files in Storage. Failed removals of queued files stay pending for a later reconciliation.
